# Deep dive: the decimal64/decimal128 initiative, and its distance from a PR

Date: 2026-10-27
Author: Claude Fable 5.1, directed by Marcelo Cantos
Scope: `marcelocantos/go@decimal64` (29 commits, 2026-02-12 to 2026-02-28, HEAD `495776b875`, based on `go1.26.0`), this repository, and the upstream discussion on [golang/go#19787](https://github.com/golang/go/issues/19787).

Method: read the proposal and roadmap; mapped and built the fork; ran its own decimal tests; wrote an independent exact-arithmetic oracle (`math/big`, IEEE 754-2008 round-half-even with preferred exponents) and ran it against the fork's operators; ran three parallel code reviews (runtime, compiler and type checker, standard library) whose reproducers were re-run by hand for every finding marked **confirmed** below; dry-ran a merge against upstream `master`; read the current state of the upstream issue. Nothing in the fork or this repository was modified. All scratch programs are listed in Appendix A.

## 1. Verdict

The initiative is in a strong position politically and a weak position technically.

- **Politically.** The upstream issue woke up this week. Owen Waller pointed the thread at this repository and the playground on 2026-10-26; a competing library author (migueldecimal128) is pushing a `decimal128` package; Marcelo replied that a deep dive and cleanup would follow. Florian Zenker (`znkr`, Go team) added a supporting data point in February. The issue carries the `LanguageChangeReview` label, so it is in the language-change review queue, not declined. Nobody else has a working compiler. That is the asset to protect.
- **Technically.** The strawman proves the *language* story: the type system, SSA lowering, ABI, reflection, generics, map keys, interfaces, and 18 standard-library packages all plumb two new numeric types through Go without breaking it. The parts that have to be *right* are not right yet:
  1. **The arithmetic core is incorrect**, not merely unpolished. decimal128 addition returns garbage for ordinary operands (`1e20 + 1e-20` gives `1.318…e18`); decimal128 division is wrong for about half of random inputs; decimal64 division silently loses digits whenever the dividend has fewer digits than the divisor (`1 / 70000000000000` prints `1.43e-14`); every width and every operation rounds twice. These reproduce from parsed strings in a plain `go run`, with no exotic inputs.
  2. **The constant model is unsound.** Quantum is carried from source literals through a string side channel in export data. It works only for a direct literal in the current package. `go/types` (gopls, vet) and `cmd/compile` disagree about whether `const b = a + 1` is a constant when `a` is a typed decimal. That is a design defect reviewers will stop at.
  3. **Public API constants were renumbered.** `reflect.Complex64…UnsafePointer` and `go/types.String…UntypedNil` shifted by two, hidden behind `api/except.txt`. The Go 1 compatibility promise forbids this; the fix is to append.
  4. The test matrix was never run: composite map keys containing a decimal crash the compiler; every 32-bit target fails to build `std`; `reflect.Value.Call` panics on `decimal128`.

**Distance.** Two different finish lines:

| Finish line | Blocking work | Estimate (one experienced engineer with current-generation agents) |
|---|---|---|
| **Design doc in `golang/proposal`** (`design/19787-decimal.md` via Gerrit) plus an honest strawman | Decide the open semantics in §6, rewrite the README sections that overstate the implementation (§5.4), republish the playground from a pinned, authenticated build | 1 to 2 weeks |
| **Reviewable CL series** (`GOEXPERIMENT=decimal`, split along §7) | Rewrite the arithmetic core once with a shared 64/128 kernel and a reference test suite; replace the quantum side channel with a real constant design; append Kind values; fix the ICEs and 32-bit lowering; rebase over 3,038 upstream commits (36 conflicting files); CL split; types testdata | 3 to 5 months of focused work, and it should not start until the design doc has had a round of feedback |

The design-doc finish line is the one to aim at now. The implementation only has to be good enough to be *honestly described*; reviewers will read the code to judge feasibility, not to merge it.

## 4. What is sound (verified)

- **Language plumbing.** Both types pass by value through calls (ten arguments), closures, channels, `defer`/`go`, method values, struct and array embedding, range loops, type switches, and generics (own `go.shape.decimal64`, not shared with `uint64`). `any(decimal64(1.0)) == any(decimal64(1.00))` is true. `switch` on a decimal matches across quanta. The SSA checker is clean on amd64 and arm64. Negation lowers to an XOR; the other operators lower to `CALL runtime.dadd64` and friends.
- **Comparison, equality, hashing.** Zero errors in 20,000 randomized comparisons per width including NaN, signed zero, and cross-quantum operands. Map keys coalesce `1.0`/`1.00`, `+0`/`-0`, and non-canonical zero. NaN keys never match. `hash/maphash.Comparable` agrees.
- **Special values.** Division by zero gives signed infinity, `0/0` gives NaN, `Inf - Inf` gives NaN, `0 * Inf` gives NaN, `x - x` gives `+0` with the minimum exponent, NaN is unordered under all six operators. Non-canonical BID coefficients are treated as zero in arithmetic, equality and hashing. Signaling NaN is recognised as NaN.
- **ABI.** The February fix (two `uint64` halves for `decimal128`) holds in compiled code; the remaining ABI defect is in `reflect`, not the compiler.
- **gob.** New type ids consume two of the reserved slots; a stream written by stock Go 1.27.3 still decodes.
- **The written proposal.** The README is well argued and well organised: motivation with evidence, the library-versus-builtin case, precedent in C23 and C#, BID versus DPD, the "why both widths" argument, a compatibility section, an implementation section, and candid open issues including the AI-assisted provenance. Most of its claims about *design* are right; its claims about *implementation status* are not (§5.4).

## 5. Findings

Severity: **blocker** stops a design-doc submission from being honest or a CL from being reviewable; **major** must be fixed before CLs; **minor** is cleanup.

### 5.1 Runtime arithmetic (`src/runtime/decimal64.go`, `decimal128.go`, `decimalconv.go`)

An independent oracle (Appendix A) computed every result exactly in `math/big`, applied IEEE 754-2008 round-half-even to 16 or 34 digits, applied the preferred-exponent rule for exact results, and clamped to the format's exponent range. Mismatches are classified as **value** (wrong number), **quantum** (right number, non-IEEE exponent), or **kind** (finite where infinity was required, or the reverse). The runtime review pass ran a second, independently written oracle and reached the same rates.

Results for operands with exponents in −10..10 and random coefficient lengths (the regime of money and measurements), 50,000 pairs per operation, as count (percentage):

| Operation | decimal64 value | decimal64 quantum | decimal128 value | decimal128 quantum |
|---|---|---|---|---|
| `+` | 554 (1.1%) | 558 (1.1%) | 3,619 (7.2%) | 0 |
| `-` | 526 (1.1%) | 553 (1.1%) | 3,668 (7.3%) | 0 |
| `*` | 426 (0.9%) | 0 | 507 (1.0%) | 0 |
| `/` | 12,091 (24%) | 4,505 (9%) | 25,783 (52%) | 1,558 (3%) |

Across the full exponent range (50,000 pairs per operation) the picture is the same with larger quantum rates: decimal64 `+` has 785 value and 22,031 quantum mismatches (44%), decimal64 `/` 10,447 value, decimal128 `+` 4,127 value and 19,502 quantum, decimal128 `/` 21,322 value plus 43 **kind** mismatches where the result should have overflowed to infinity.

Confirmed root causes, with one-line reproducers that use `strconv.ParseDecimal64/128` so no constant encoding is involved:

Structural: the two files are the same roughly 1,000-line program written twice with `uint64` swapped for a hand-rolled `uint128`; `softfloat64.go` does two widths in 600 lines with one core. Dead code includes `bid64IsSpecial`, `bid64Zero`, `bid64RoundToNDigits`, an unreachable branch in `ddiv64` (`:334-361`), and a discarded first loop in `u128NumDigits`. The runtime imports `internal/strconv` to format a `float64` and re-parse its digits as its float-to-decimal algorithm. Thirty-five functions carry `//go:nosplit` with no justification. Comments assert compliance the code does not have. No arithmetic test exists in `runtime`; `test/decimal.go` checks `10/3` "approximately". Nothing runs against an external vector set.

**Assessment.** This is not a bug list to work through; it is a rewrite of one kernel: exact integer result (128 or 256 bits), one half-even rounding with a true sticky bit, preferred-exponent selection, clamp and overflow, shared between the two widths. Then validate against the Speleotrove `decTest` suite (`ddAdd`, `ddMultiply`, `ddDivide`, `dqAdd`, …), which is exactly what ROADMAP Phase 1 already says and what the competing library already does.

### 5.4 Claims in the README that do not hold

These need editing before anyone on the Go team reads the document, because each one is checkable in a minute and each one damages credibility.

| README says | Reality |
|---|---|
| "A complete implementation exists — not just a prototype." "The implementation is complete but needs IEEE 754 conformance testing" | The arithmetic core is incorrect on ordinary inputs (§5.1). Say "a working strawman that demonstrates integration; arithmetic is known to be non-conformant pending a kernel rewrite". |
| "Access to the new types is gated by the `go` directive in `go.mod`, following the precedent set by `any`" | No gating exists (C6). |
| "`const c = 1.50; var d decimal64 = c` does preserve [quantum]" | Only within the declaring package; lost on import, in multi-name declarations, and in any computed constant (C2). |
| "Typed decimal constant expressions are evaluated by the compiler using the runtime's BID arithmetic" | They are rejected as non-constant by `cmd/compile` and accepted by `go/types` (C1). |
| "`math`: `Abs64`, `Abs128`, `FMA64`, … `Decimal128NaN`, `IsDecimal128NaN`" | Names are `Decimal64Abs`, `Decimal64FMA`, …; both widths have NaN/Inf helpers (L5). |
| "Hashing normalizes trailing zeros" with "Hash normalized components" | Correct in effect, but the sign byte written to the hash is always zero (`buf[0] = byte(sign)` where `sign` is `0` or `1<<63`), so `x` and `−x` always collide. |

## 6. Decisions to make before the design document

Each of these is a design question the implementation currently answers by accident. The design doc should state the answer; the strawman should then be made to match.

1. **Constants.** Either (a) untyped constants carry no quantum, conversion to a decimal type yields the canonical shortest form, and the runtime agrees (drop `origLit`; simplest; loses `var d decimal64 = 1.50` printing as `1.50`), or (b) add a decimal constant representation to `go/constant` (coefficient and exponent, exact) so quantum is part of the value, `go/types` and `cmd/compile` share it, and typed decimal constant expressions fold exactly. (b) is the honest version of what the README promises; it is also a `go/constant` API change and must be in the doc. Either way, typed decimal constant expressions must fold or the spec must say why they do not.
2. **Default formatting.** Does `%v`/`String`/JSON print the quantum (`1.50`) or the shortest form (`1.5`)? IEEE and every peer language print the quantum. If shortest is chosen, the proposal loses its best demo; if quantum is chosen, `%#` returns to its float meaning and `IsZero`, `omitempty`, and `reflect.DeepEqual` need stated semantics.
3. **Where the helper functions live.** `math.Decimal64Abs`×44 versus a `math/decimal` package (generic over `~decimal64 | ~decimal128`, with `Quantize`, `Round` with explicit rounding modes, `Mod`). The latter also answers Marcelo's own comment on the thread about rounding modes living in a standard package.
4. **Rounding modes and sNaN.** State that operators are round-half-even only, that sNaN is accepted and quieted, that NaN payloads are not propagated; put directed rounding in the helper package.
5. **Conversions.** `float64 → decimal`: exact binary value (IEEE) or shortest round-trip digits (current, Go-flavoured, defensible)? `decimal → int` on overflow and NaN: implementation-defined like floats, or specified? Rune and hex-float literals assigned to decimals (C3) are a spec question, not just a bug.
6. **Widths.** decimal128 only, both, or all three. The thread leans decimal128-only; the README argues both. The "decimal64 is nearly free once decimal128 exists" argument is correct only with a shared kernel, which the current code does not have.
7. **Rollout.** `GOEXPERIMENT=decimal` for one release, as the ROADMAP says; and whether the first CL series ships `reflect.Kind` additions at all or hides them behind the experiment.
8. **Wire formats.** `encoding/binary` and `gob` byte order for decimal128; JSON exponent-form thresholds.
